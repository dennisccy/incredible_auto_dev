## 36. An aggregate verdict written beside a concurrent authoritative lane reports a false green

**Applies to:** any report whose verdict gates later steps (QA → audit → closure → "ALL CHECKS PASSED") while another lane that the phase's DEFINITION OF DONE depends on runs in parallel or independently — the QA validator versus the browser-qa lane in run-phase.sh's post-dev fanout, and any future "summary" verdict over lanes it does not own.

**Pattern:** goal-taketwo iter 12 (2026-09-23). The post-dev fanout ran the QA validator concurrently with the browser lane. The browser lane finished `Browser QA Verdict: FAIL` — the target journey J-06 and the required journeys J-02, J-04 and J-09 red. The QA agent, whose own browser work was three spot-check screenshots, wrote `**Verdict:** PASS`, "Browser Checks ✅" and "All validations passed", never citing the lane. `verdict_passes` read that PASS, so run-phase.sh skipped the Step 7 loop, `phase-audit.sh` (which requires a passing QA verdict) ran, closure passed and the phase printed "ALL CHECKS PASSED". Nothing was fabricated; the aggregate simply did not account for the authoritative lane. Only the independent auditor noticed (P1), and only by reading both files.

**Why it fails:** the QA agent CANNOT reliably see the lane: in the fanout it often finishes first (iter 12: QA report 17:15, merged lane verdict 19:50). An instruction to "read the browser results" is therefore necessary but never sufficient — the only place that sees both final verdicts is the engine, after the join. And because `verdicts.check_verdict_file()` accepts ANY `**Verdict:** PASS` line in a report, rewriting only the first verdict line would leave the report passing.

**Prevention:** a deterministic post-join gate, `scripts/automation/lib/qa_lane_gate.py`, called by run-phase.sh wherever a QA verdict is read: every Step 7 attempt, a verdict already on record before Step 7 is skipped (fanout pass or a resume checkpoint past QA), and the Step 9 hardening QA re-run — failing closed when the gate itself cannot run. It re-assesses the lane on every apply: a gate section on record never exempts a report (a closure_failed resume re-runs the lane but not QA). When the browser lane is required (frontend present, maintenance isolation not declared), a passing QA verdict survives only if the lane meets the phase DoD. A missing, unparseable or SKIPPED lane, a failing journey row, or a failing (or skipped) check that the PRE-RUN UI test plan marks P1 or does not list (priorities come only from the plan, never from the executing agent's results table — anti-pattern 25) rewrites every passing verdict line (the first to `**Verdict:** FAIL`, the rest to `**Agent verdict (overridden by the browser-lane gate):**`) and appends a `## Browser lane gate (deterministic)` section naming the lane file and every non-PASS row. When the only failing rows are checks the pre-run plan marks P2/P3 (goal-taketwo iter 13: a test-plan expectation with no basis in the goal), the verdict stands but is recorded as `PASS_WITH_NOTES` with every such row cited, so the report can never again read "all validations passed" beside a red row. The first, strict version blocked on ANY failing row; iteration 13 showed that starves every iteration of its audit whenever an exploratory P2 check finds an unrelated, pre-existing behaviour. The browser result itself is never touched or converted. A QA failure is then retried in the way that can change it. The first version failed `qa_failed` outright, while an agent-written FAIL entered a fix loop that never re-ran the lane — every retry was spent on a verdict that could not change (review, 2026-09-29). Now: when the gate alone failed QA (it overturned the agent's PASS) and the lane produced no usable evidence (SKIPPED / MISSING / UNPARSEABLE), only the lane re-runs, with no dev fix; every other failure (the agent's own FAIL, failing lane rows) gets dev fix + review, then the lane re-runs on the fixed code before QA retries whenever it fails the DoD; a verdict on record that the gate overturns re-opens the QA loop at its fix step and re-runs every later step that trusted it; a `qa_failed` resume re-runs a lane that gave no usable evidence before QA; a lane status that cannot be read fails closed, and quota that outlasts a lane re-run's waits stops the phase resumably (exit 75) instead of spending QA attempts on a missing lane. Rule: every verdict that gates a later step must be recomputed or checked by the engine against every lane it summarises, at the point where all of them are final — never trusted from an agent that may have written it before the lanes finished (`qa_lane_gate.py self-test`, `tests/automation/test-qa-lane-gate.sh`, which reproduces the iter-12 false green against the unpatched engine).

**Detection:** a QA report reading PASS while `reports/phase-<phase>-ui-test-results.md` reads FAIL or SKIPPED; a QA report whose `Browser checks` section never names the lane; an audit report correcting a QA verdict; "ALL CHECKS PASSED" in a log whose browser lane was red.
